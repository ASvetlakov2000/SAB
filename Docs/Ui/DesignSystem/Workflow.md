# Обязательный workflow каждой UI-задачи SAB

Канон: [STATUS](STATUS.json), [Specification](Specification.md), [ErrorRegistry](ErrorRegistry.md). Этот файл задаёт процесс проверки, не второй визуальный стандарт. Роли: [ReviewRoles](ReviewRoles.md). Применяется к новому окну, изменению существующего, secondary settings и общим компонентам; объём определяется задачей пользователя.

## До XAML/C#

1. Прочитать рабочие/вложенные AGENTS, repo skill и канонические файлы; проверить Git status и сохранить затрагиваемые незакоммиченные изменения. Не повторять аудит36 окон или концепции. Если pending/productionMigrationAuthorized=false — не переносить черновик и не устанавливать его. Уточнение очереди не разрешает выполнение.001–010/048/056.
2. Разобрать реальный C#/XAML/VM/commands/API context. Записать задачи пользователя, обязательные поля, состояния, зависимости, способы ввода/сохранения, основное/вторичное действие, область работы и все secondary windows. Новые функции отделить от оформления.001/004/005/053/054.
3. Выбрать [Layout Pattern](LayoutPatterns.md), заполнить [Layout Specification](LayoutSpecification.md) с wireframe до кода; сложному окну сравнить2 структуры. Общий стиль не означает одинаковую геометрию всех окон.008/012/027/049/050.
4. Назначить каждой изменяемой части общий resource owner; свериться с текущим coverage, не со старой Gallery. Записать применимость **каждого** ID из реестра. Нет таблицы — table-ID N/A с причиной; нет среды для проверки — NOT RUN, а не N/A. Уже существующие дефекты в затронутой части включить в scope/отчёт, не скрыть как baseline.003/006/011/048/056.
5. До реализации подготовить критерии результата и матрицу снимков: normal/minimum, длинный русский текст, применимые состояния, dropdown/focus/edit/empty/validation, прокрутка/last column, secondary windows. Разделить preview/runtime/production/OS DPI/physical input.009–011/018/025/047/058.

## Реализация

- Использовать канонические resources/components и выбранный pattern. Не менять функции/контексты ради вида. Новое общее решение добавить в resource owner и coverage.003–005.
- Проверить основные группы риска: таблицы013–019; капсулы/вкладки020–025; карточки/формы026–035; поиск/действия036–041; инструкции/metadata042–044; scroll/gutter045–046; captured picker047; coverage048; дополнительные сценарии049–058. Это указатель, не замена полного списка ID.
- Новое замечание пользователя сохранять с источником/изображением, следующим устойчивым ID и воспроизводимым критерием. Исправлять общий компонент и добавлять подходящую проверку; если дефект локален по функции, документировать границу вместо неверного глобального правила. Обновить общие шаблоны/критерии в том же разрешённом объёме.056.

## После реализации

1. Собрать реально затронутые target configurations. При UI-изменении запустить **фактическую изменённую поверхность**, получить native screenshots с происхождением. Preview отдельной DTO-копии не доказывает рабочий production-класс. При документировании без UI/host/test изменений повторная тяжёлая сборка не обязательна — ссылаться на существующий протокол как старое доказательство.005/007/009/010.
2. Сверить capture с назначением: видимый target, настоящий open popup/edited state, settled animation, актуальные размеры/ресурсы. Пустой/неверный обязательный capture → recapture, без вердикта качества по нему. Не менять бизнес-логику ради красивого снимка.009/025/047/052.
3. Проверить все применимые ID по критериям реестра, а также матрицу новых состояний/данных. Для геометрии измерять реально видимые части и допуск из спецификации; static resource setter не считается измерением. Snapshot проверить глазами; build-pass не visual-pass.011/014/016–019/021–025/028–035/045–047.
4. Builder выполняет один собранный проход дефектов, исправляет найденное пакетом, подтверждает затронутое. Независимый reviewer делает full review разрешённого scope; после fix тот же reviewer оценивает только исправления и внесённые ими регрессии. Новое противоречащее пользовательское evidence/новый scope требует fresh full review. Не устраивать бесконечный поиск косметики. [Контракт](ReviewRoles.md).
5. Documenter сверяет документацию с фактическими ресурсами/Compile/новыми доказательствами, обновляет DESIGN/sidecar/coverage/registry. Он не рисует доказательства и не объявляет недоказанный production PASS.048/056.
6. Завершить отчёт по всем ID. FAIL устранить либо явно оставить открытым с причиной/следующим шагом; NOT RUN раскрыть. Нельзя заявлять полную готовность/приёмку, если обязательный существенный критерий остался FAIL/NOT RUN. Scope verdict reviewer не расширять.006/007/009/010/056.

## Формат отчёта

На каждую задачу копировать [WorkflowReport.template.json](WorkflowReport.template.json) в её каталог доказательств, заполнить заголовок и **все ID**. Это пустая форма, не протокол0.5 и не58 новых PASS. Исторический протокол0.5 имеет75 программных PASS и27 PNG; сопоставление его частичного покрытия дано в реестре.

| Поле | Правило заполнения |
|---|---|
| status | Только PASS / FAIL / NOT RUN / N/A |
| applicable | true / false; null допустим только в незаполненном шаблоне |
| scope | documentation / preview / production; при нескольких scopes отдельное evidence с явной границей |
| reason | Обязателен для FAIL/NOT RUN/N/A; N/A объясняет отсутствие самого сценария, не невозможность запуска |
| evidence | Для PASS обязательны конкретный файл/снимок/команда+результат/измерение и версия; ссылка на наличие стиля сама по себе не закрывает runtime |
| unverified | Явные ограничения: другие данные/состояния/DPI/Revit/physical input, если остались |

Для каждой UI-задачи фиксировать: source revision/dirty baseline, дату, scope, readFiles, выбранный pattern/brief, build commands+exit, surfaces/viewports/states, capture hashes, runtime vs render DPI, source-contract, independent verdict и его границы, approval/migration status. Не делать универсальное обещание «ошибок больше не будет».

В конце: кратко что изменилось, почему, что проверено, какие ограничения остались и ссылка на реальные снимки/отчёт. Обычные design decisions не возвращать пользователю для согласования; новое approval требуется только по действующему scope/STATUS и прямым указаниям.

## Проверка самих документов

`python Tools/UiShowcase/ValidateUiDocs.py` проверяет ID/ссылки/форму/coverage и существующий evidence, не запускает WPF и не даёт UI-verdict. Для заполненного отчёта добавить `--report <path>`; валидатор проверит структуру/полноту, но не истинность скриншотов. Review по существующим ролям остаётся нужен.
