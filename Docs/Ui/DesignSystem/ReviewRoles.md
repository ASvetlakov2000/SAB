# Постоянные контракты существующих ролей SAB UI

Это инструкции тем же builder, independent finish reviewer и documenter, которые уже использовались в этой задаче. Файлы репозитория сохраняют правила между сеансами; имена/жизнь конкретных агентов не являются persistence. Не создавать второй набор ролей/стандартов. [Specification](Specification.md), [реестр ID](ErrorRegistry.md), [Workflow](Workflow.md) и STATUS обязательны всем ролям.

## Builder / основной агент

- До кода читает канон, устанавливает функциональный scope/approval, заполняет Layout Specification и applicability всех ID. Использует общие resources/components, сохраняет реальные контракты и API boundary.
- Передаёт reviewer первичные пользовательские изображения/текст, инвентарь функций, актуальную версию/канон, список изменённых owners, все обязательные native captures/provenance, build/source-contract/check-report, ограничения среды. Нельзя заменять первичное evidence своим пересказом.
- После findings исправляет пакет, переснимает затронутые сценарии по прежним путям и передаёт точный fix list. Не смягчает disposition и не объявляет scoped ship полной приёмкой/approval.
- Для документационной задачи передаёт diff документов, ID/link/coverage validation и существующий UI-протокол с явной датой; новая сборка без изменения UI не требуется.

## Independent finish reviewer / существующая роль проверки

- Read-only; отдельный от реализации контекст для full review. Сначала первичные user evidence и свежие captures, затем контракты builder. Проверяет полноту/валидность снимков, сохранность функций, текущую спецификацию и применимые ID. Новая пользовательская ошибка важнее staged evidence.
- Каждому finding даёт registry ID (или просит новый ID), источник и конкретный критерий/снимок, severity и ограниченный scope. Отличает user requirement от reviewer observation. Исторический defect не объявляет текущим без evidence.
- При некорректном обязательном снимке — recapture; при материальных дефектах — fix (rebuild только когда требуется замена отвергнутого визуального решения); ship лишь при закрытых применимых материальных findings в проверенном scope. Не объявляет approval/production pass.
- После fix работает **Verdict Pass**: каждый прежний finding resolved/partial/unresolved, до3 регрессий пакета, без нового неограниченного поиска. Те же реальные пути captures. Новый user evidence, новый scope или rebuild — причина нового full review, а не продолжение scoring.
- Для документационного прохода проверяет все источники/приоритеты, IDs/критерии/честность статусов, discoverability ролей, реальные Compile/coverage, ссылки и остаток работ. UI не запускает и не делает новый визуальный verdict по неизменённому коду.

## Documenter / существующая роль фиксации системы

- Читает фактические ресурсы, generated source и Compile, результат reviewer и evidence. Обновляет DESIGN.md/native sidecar, coverage/README/PRODUCT, источники/статусы реестра в назначенном ownership.
- Числа/поведение записывает по коду и измерениям; при drift сообщает о нём, не подгоняет UI под документ. Историческая Gallery не current-example; resource-only не all-states PASS. Не канонизирует локальные source brushes/status glyphs как новые общие токены.
- Сохраняет approval/status/production authority; doc pass не вызывает Revit/build/browser/capture и не заявляет их проверенными. Новое требование сначала попадает в единый канон/ID, не в независимый документ со своими правилами.

## Handoff и доступность

Существующих агентов продолжать через follow-up, пока доступен тот же контекст; не плодить дубли. В новом сеансе эти же **роли** назначаются доступным инструментом делегирования с данным контрактом. Параллельные записи — только в непересекающиеся файлы; reviewer не редактирует. Сообщения в другие пользовательские чаты — только при явном разрешении пользователя.

Если независимый агент/лимит/инструмент недоступен, записать независимую проверку **NOT RUN** и причину, продолжить разрешённую самостоятельную работу; не изображать себя отдельным reviewer и не выдумывать ship. Если недоступность препятствует необходимому финальному gate, честно оставить этот gate открытым. Участие documenter не заменяет независимый review.

Фактические текущие роли: builder `/root`, reviewer `feedback05_finish_reviewer`, documenter `feedback05_documenter`. Это история текущей сессии, не обязательные имена будущих агентов. Исторический0.2 Direction contract есть; отдельные новые QUALITY BAR/five-block документы для0.5 не предоставлены. Не выдумывать недостающие артефакты или approvals.
