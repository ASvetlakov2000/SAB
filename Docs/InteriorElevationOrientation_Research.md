# Ориентация и обрезка развёрток SAB

Дата:15.10.2026. Источник: текущий код рабочего SAB, локальный dirty baseline сохранён в `outputs/ui-production-preview/elevation-research-baseline`. Исследование кода и арифметические контрпримеры; воспроизведение в Revit2022–2024 не выполнялось. Независимая read-only проверка подтвердила перечисленные дефекты. В этом изменении реализованы нумерация и загрузка семейств; геометрические исправления ниже — рекомендации для следующего изменения.

## Основная причина разворота

`ElevationMarkerService.CreateElevationForLine` каждый раз создаёт новый маркер и первый доступный индекс, затем `RotateMarkerToDirection` совмещает ViewDirection с InsideNormal. Большой угол выполняется одним `RotateElement`. После регенерации любое несовпадение `dot<0.99` вызывает ещё один поворот ровно на180°. Это условие не означает, что направление противоположно: ошибка10° также проходит условие и превращается примерно в170°. Если направление всё ещё неверно, код только пишет warning и возвращает вид; `ElevationViewCreationService` считает его созданным.

Autodesk исторически подтвердила дефект большого поворота ElevationMarker, REVIT-134773, с дополнительными180°; в той же ветке приведён обход малыми шагами30°. Дефект описан для старых версий Revit; это сильная гипотеза механизма, но не доказательство его наличия в конкретном установленном2022/2023/2024. [Первичный отчёт и ответ Autodesk](https://forums.autodesk.com/t5/revit-api-forum/elevationmarker-does-not-rotate-180-deg/td-p/8010880).

В SAB уже существует другой алгоритм: `ElevationFlipService.RotateMarkerByChunks` дробит ручной разворот на30°. Создание фасадов этим обходом не пользуется. Кроме того, при создании нет явного `Regenerate` между `CreateElevation` и первым чтением ViewDirection; свежесть направления следует проверить отдельно в живом Revit. Даже дробление без итоговой проверки не гарантирует результат.

Решение: общий сервис совмещения направления для создания и разворота. После создания — Regenerate; вычислять знаковый остаточный угол через `atan2(cross.Z,dot)`, вращать шагами≤30° с регенерацией, затем заново читать фактическое направление. Допуск задавать по углу, например0.1°. При остаточной ошибке — ограниченное число точных коррекций; при провале откатывать только текущий маркер/вид в SubTransaction, сообщая actual/target/angle. Безусловный PI fallback убрать. Проверку повторять после настройки crop и перед фиксацией транзакции.

Знак нормали инвертировать не нужно. В Revit `ViewDirection` направлен **к наблюдателю**, а не от камеры к стене. Маркер внутри комнаты должен иметь ViewDirection от стены в комнату; текущий знак InsideNormal соответствует этому. [Autodesk ViewDirection](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/822149b4-d843-3370-286b-c3bc8c82abff.htm).

## Тонкие стены, два фасада и распознавание стены

В `LineOrientationService` нет чтения толщины стены, её грани или направления. Сторона определяется двумя точками по±150мм от середины линии в объёме **выбранного** помещения. Если обе проверки совпали, используется направление к `Room.Location`, названной в коде центром комнаты. LocationPoint — точка размещения помещения; она не определяет внутреннюю сторону каждого участка вогнутого контура. Высота проб целиком берётся из линии. `IsPointInRoom` проверяет объём, поэтому невернаяZ может превратить обе пробы вfalse. [Autodesk IsPointInRoom](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/96e29ddf-d6dc-0c40-b036-035c5001b996.htm).

Контрпример: Г-образная комната `(0<x<4,0<y<1) ∪ (0<x<1,0<y<4)`, точка помещения `(3,0.5)`. Линия в400мм стене при `x=1.2,y=2.5`: пробыx=1.05/1.35 обе вне комнаты, fallback выбирает+X, хотя помещение слева. Для100мм стены при линииx=1.05 одна пробаx=0.90 внутри, другаяx=1.20 снаружи — сторона определяется правильно. ПриZ вне комнаты даже тонкая стена получает двеfalse-пробы.

Поэтому тонкая стена и наличие второго фасада сами по себе не подтверждены как причины. Для каждой линии создаётся отдельный маркер; соседний фасад не участвует в выборе стороны. Возможная связь косвенная: положения линий относительно отделки, узкие участки помещения, неправильная комната/Z, смещение маркера либо автоматическое поведение Revit при регенерации.

`MarkerPoint = MidPoint + InsideNormal * MarkerOffset` не проверяется на принадлежность комнате. Даже верно выбранная нормаль при большом смещении может поставить маркер за противоположной границей. Это особенно существенно для узких ниш; для двух сторон стены следует проверять две отдельные комнаты и две точки маркеров.

API `CreateElevation(document,planId,index)` не требует передавать стену: направление определяется индексом, исходные границы наследуются от плана. Поэтому версия «API не может создать фасад, пока не почувствует стену» не подтверждается контрактом. Зависимость внутренних эвристик Revit и начальной обрезки от модели исключить нельзя. [Autodesk CreateElevation](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/ef15bad0-1f09-2a61-b74b-f4967137a47b.htm).

Решение выбора стороны: пробы в нескольких точках вдоль линии (например25/50/75%) и на нескольких расстояниях5/20/50/150мм, сZ заведомо внутри выбранной комнаты в её системе координат. Если линия проходит внутри толстой стены, расширять расстояние в разумных пределах и сверяться с ближайшим сегментом контура/гранью выбранного помещения. При неоднозначности не выбирать сторону молча по LocationPoint: откатить конкретную линию с диагностикой. Проверять MarkerPoint в той же комнате; при невозможном заданном смещении сообщить причину либо явно согласованно ограничить смещение. В связанных моделях сохранять существующие преобразования host↔link.

## Почему неверна ширина обрезки

`ElevationCropService` сначала вычисляет `minX=startLocal.X-left`, `maxX=endLocal.X+right`, затем сортирует результаты. Начало линии не обязано быть экранной левой точкой; при противоположной ориентации или обратном направлении рисования порядок меняется.

Дляx0=3000,x1=0мм,left=50,right=100 текущий результат `[100,2950]`, ширина2850мм. Правильная экранная обрезка `[-50,3100]`, ширина3150мм. Даже одинаковые отступы50мм дают2900 вместо3100мм. Это самостоятельный дефект; он возможен и без ошибки Revit.

Решение: после окончательного выравнивания и Regenerate получить актуальный CropBox.Transform; перевести оба конца в его координаты, сначала взять min/max, затем применить соответствующие экранные отступы. Проверить итоговую ширину по фактическому crop. Не использовать знак направления исходной линии как гарантию экранного порядка. Пользовательские левые/правые отступы следует трактовать в системе текущего вида.

## Почему обрезка смещается после180°

`ElevationFlipService.CaptureViewState` сохраняет local Min/Max, но не исходный Transform. `ApplyViewState` записывает те жеXY в новый базис после зеркалирования/поворота. `DoesCropMatch` сравнивает те же локальные числа и может подтвердить физически неверную область. Проверка становится частью ошибки.

Пример: исходный localX=[−1,3], осьX совпадает с мировой. После180° осьX меняет знак. Для прежней физической области новый localX должен быть[−3,1]. Копирование[−1,3] даёт мировую область[−3,1]; нынешний validator возвращаетtrue. Симметричный crop=[−2,2] маскирует проблему. При перемещении маркера меняется также origin, поэтому одного изменения знака недостаточно.

Решение: сохранить старый Transform и все углы прямоугольника в модельных координатах. После операции перепроецировать их в новый базис через новый Transform.Inverse; заново вычислить min/maxXY. Для произвольной формы преобразовать все кривые на актуальную плоскость вида; один старый CurveLoop без согласования плоскости не гарантирует сохранение. Проверять модельное положение углов/ширину/высоту, а глубину — отдельно относительно выбранной линии. Явно определить, сохраняется физическая область по стене либо зеркалируется область относительно опорной линии; для180° с перпендикулярной линией горизонтальная проекция на стену должна сохраняться. Fallback-поворот вокруг маркера не переносит маркер на другую сторону линии и также требует отдельной проверки.

## Реализованные изменения и проверка

Нумерация: поля «Префикс» / «Суффикс» после наименований в той же карточке, живой пример и сохранениеschema15; старые настройки получают суффикс`-Р`. Пример`ЭЛВ-1-А, ЭЛВ-2-А`; при занятой группе`ЭЛВ-1-А-2, ЭЛВ-2-А-2`. Уникальный общий суффикс резервируется по всем viewport документа, включая листы продолжения. Исходный индекс линии сохраняется: настоящие ошибки создания не скрываются перенумерацией. Разворот и перенос сохраняют системный номер. Уже существующие виды автоматически не перенумеровываются; для неразмещённых видов номер viewport ещё отсутствует.

Семейства: удалена принудительная перезагрузка двух марок вRevit2022 с overwriteParameterValues=true. Сначала загружаются сохранённые настройки/предпочтения, затем проверяются выбранные типы в документе. Существующее выбранное пользовательское семейство удовлетворяет соответствующей роли; встроенная замена не загружается. Если выбранного типа нет, используется уже загруженное стандартное семейство; отсутствующее стандартное загружается один раз. Файл на диске не требуется для семейства, которое уже есть в модели. Валидация категории аннотаций сохранена.

Контрпримеры: `Tests/InteriorElevations.Numbering/GeometryCounterexamples.py`,12арифметических проверок. Нумерация/загрузчик: `Tests/InteriorElevations.Numbering`,20проверок фактических сервисов на stub Revit API. Фактическое WPF-окно иJSON: `screenshots-elevation-numbering/verification.txt`; границы проверки — вне Revit. Сборка/MSI и независимый UI review фиксируются в отдельном ElevationNumbering-Report.json.

Следующий Revit-прогон геометрии: стены50/100/200/400мм; обе стороны общей стены по отдельности и вместе; изменение направления рисования линии; углы0/90/135/170/180/190/270°; Г-образная комната/ниша/линия вне стены; связанная комната с transform; смещение маркера0/250/больше ширины ниши; асимметричные отступы50/100 и crop, уже сдвинутый относительно центра; разворот на плане и на листе. В журнале нужны room/link/line/marker/view IDs, версии Revit, координаты/Z, обе пробы, fallbackreason, target/actual direction, requested/actual angle и оба CropBox.Transform. Только этот прогон сможет связать исторический дефект Revit с вашими конкретными тонкими стенами.
